Every arrow on the last slide is a ring: a fixed array that one thread writes and one thread reads, each moving only its own position counter, so there is no lock and nothing is allocated per message. Why not skip the hand-off? The direct call in the table is the engine with nothing else to do. In the real system three jobs happen for every message: the engine matches it, the log writer encodes it and writes it to disk, and the standby matches it again to check. At full speed, 5.5 million messages a second, the engine thread spends about 180 ns a message, and the log writer and the standby keep their own cores 70 to 100% busy, about 150 and 170 ns of work per message. Today those run in parallel on three cores. Without rings, one thread would do all three in a row: about 500 ns a message, so about 2 million messages a second instead of 5.5. That is arithmetic from the measured CPU use, not a separate run. The ring costs about 40 ns per hand-off to move about 320 ns of work off the engine’s core. And the input still arrives from other threads, so some hand-off is unavoidable. Channels are slower because their reader goes to sleep and the operating system has to wake it. What the ring costs. Memory: rings are allocated up front at their full size; ours hold 64k records each, about 15 MB in all, roughly half the process. One writer and one reader only: to feed the log and the standby we keep one ring each and copy every record into both. Bounded: when a ring fills, something has to give, and we choose per reader: the log and the standby make the engine wait, the UI drops. Waiting: our readers spin for a moment, then nap 50 µs, so an idle system costs nothing but a quiet one adds up to 50 µs. Upkeep: it is a small, well-used crate, but its unsafe code is something we trust rather than read, and the pattern is less familiar than a channel. So we use it only on the hot path; the web edge uses ordinary tokio channels, where microseconds don’t matter.
