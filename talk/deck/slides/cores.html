Other programs using about 4 cores’ worth of CPU (busy) or 7.4 of the 8 (heavy).

Why it slows down

The M3 has 4 fast and 4 slow cores. When the fast ones are taken, macOS moves the engine to a slow one, and its data has to be fetched again.

The fix

macOS can only ask for priority. Linux can reserve a core for one thread, and nothing else runs there.

Measured: cargo run --release -p bench -- engine, Apple M3. Not a controlled test: “busy” was Spotlight indexing, “heavy” another simulation of ours running at the same time.

The bars are the engine’s cost per message on the recorded Monday-open flow. “Busy” means other programs were using about 400% CPU, four cores’ worth; “heavy” means about 740%, nearly all eight. Those loads were not planned: Spotlight was indexing during one set of runs and another of our simulation runs was using the machine during another, so treat the exact numbers as indicative. Why sharing hurts: the M3 has four performance cores and four efficiency cores, which run at a lower clock with smaller caches. A thread does not own a core; the operating system decides every few milliseconds who runs where. When other programs take the performance cores, macOS moves the engine to an efficiency core, where it starts with cold caches and a slower clock: the cost per message doubled, 35 to 75 ns. Asking for top priority (user-interactive QoS) kept it on a performance core under the busy load, under 1% change, but not under the heavy one: priority is a request, not a reservation. On Linux you can reserve: pin the engine thread to one core and remove that core from the scheduler, so nothing else ever runs there. That is the conclusion that feeds the deploy slide: the engine thread gets a core to itself.
