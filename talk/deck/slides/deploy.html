So how do you deploy it? · two machines × 20 cores

One book, one core. Scale by adding books.

1 core per book. 5.3–5.7M msgs/s flat out. A second core on the same book only adds a lock.

Helpers share cores. Standby and log writer need most of a core each flat out; at real-market rates they idle.

Route, don’t balance. The balancer only spreads load over gateways. Each order then goes to its ticker’s one core.

Each hop in front adds microseconds inside one region; a block is 250 ms. 15 books a machine is illustrative, not a capacity plan we tested.

This answers the question the last few slides raise: with two machines of 20 cores, how do you lay it out? A book is one stock’s order book. Its matching is strictly sequential, so it lives on one thread, and the lock benchmark showed that adding a second thread to the same work only makes it slower. One core is plenty: one engine thread holds 5.3 to 5.7 million messages a second, which you will see live in the demo. So the way to use a big machine is many books, each on its own reserved core, the way an exchange runs many stocks. Each core runs that book’s sequencer and its matching, because in our design the sequencer is per book, on the same thread, so it scales with the books for free. The helpers, the standby and the log writer, need most of a core each flat out but are nearly idle at real-market rates, so they share the leftover cores with the network edge and the operating system. In front sit gateways: they take connections, check orders and route each one by ticker. A load balancer can spread traffic over the gateways, because they hold no state, but never over books: every AAPL order must reach the one AAPL core, or there is no single order of events. Each of those hops costs microseconds inside one region, nothing next to a 250 ms block, so add them when you need them, not before. The second machine buys fault tolerance, not speed: every record is copied there, and a standby for each book is ready to take over. One caveat for on-chain venues: the chain itself has one sequencer that orders every transaction for every book, so that shared step is the chain’s scaling problem, not the matching engine’s. And 15 books a machine is an illustration, not a capacity plan we tested on 20-core machines.
