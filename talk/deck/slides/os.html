Threads, cores and memory

What the OS does to a hot thread

A hot thread never stops working and every order waits for it, so any time it loses, every order loses. Ours is the engine thread. It runs fast only while its data stays in the core’s cache.

Warm vs cold: a thread moved to another core finds its data cold and fetches it again.

Production · Linux

  • Pin the thread to a core: taskset, sched_setaffinity
  • Isolate the core: isolcpus, nohz_full
  • Route interrupts elsewhere: IRQ affinity
  • Real-time priority: SCHED_FIFO
  • One writer per core, as LMAX did

macOS can only ask (QoS). Linux can reserve. Our numbers: allocations down to ~0 per message; a stress run uses ~30 MB.

Optional slide: keep it to 45 seconds. Start with the definition: a hot thread is one that is busy all the time and sits on the critical path, so every order waits on it. Ours is the engine thread: it handles every message, one after another, so if it stalls for a microsecond, every order in the queue is a microsecond late. Hot also describes its data: what it touches on every message, the top of the book and its order index, is kept in the core’s small fast caches, and stays warm only while the thread keeps running on that same core. The engine’s work per message is a fraction of a microsecond, so where its data sits matters. On the M3, each performance core has its own small L1; the four performance cores share a 16 MB L2; then a system cache and RAM, each several times slower. All figures approximate. A thread that stays on one core keeps its data warm. Moved between performance cores it loses only L1; moved to an efficiency core it loses everything, which is what QoS mostly prevents. Production systems run on Linux and go further: pin the thread, take the core away from everything else, send interrupts elsewhere, give it real-time priority, and keep one writer per core, as LMAX did. Our own numbers: allocations per message went from 1.3 to between 0.001 and 0.16, and a stress run stays around 30 MB.
