# Decisions

Choices made where SPEC.md was ambiguous or silent, one line of reasoning each. Entries marked
**Spec issue** are places where the spec looks wrong or contradicts itself; they are recorded
here, not silently changed.

## Engine and log format

1. **Order id = the `seq` of the `New` record.** The spec's record has no order-id field for `New`, and `seq` is already unique and deterministic.
2. **The engine uses `agent` for self-trade prevention and cancel ownership, never for priority.** Section 5 requires cancelling the resting order on a self-trade, which needs the owner; a cancel from a non-owner is a reported no-op.
3. **Extra events: `Accepted` per `New`, and `Rejected` for malformed records** (zero quantity, price ≤ 0, `seq` not increasing). Agents need `Accepted` to learn their order ids; rejecting beats panicking on bad input.
4. **A cancel for an order that isn't resting gives one `CancelMissed` event**, without saying whether it was filled, cancelled or never existed. Simplest reading of "a no-op that is reported".
5. **`BookChange` is emitted after every level change, with the level's new total**, not coalesced per message. "An event on every book change", literally.
6. **`Cancel{order_id, priority_fee}` (spec rev 36), and LP β ≠ 0 is allowed.** The fee is in the log (format version 2), PGA sorts cancels by it like any message, and the sender pays it to the chain when the cancel is included, whether or not it finds the order. Under PGA the LP bids β × exposure on each cancel, where exposure = max(0, staleness against the LP's last seen price) × remaining lots: what a sniper could take from that quote, mirroring the sniper's α × expected prize. With the default β = 0 nothing changes: every golden *fills* hash is unchanged; all 36 *log* hashes changed, because the format version and the new field are part of the encoded log.
7. **The input log on disk is postcard of `{format_version, scenario, seed, config_toml, records}`.** The engine has no serde, so `sim::log` mirrors the record type. Embedding the config makes a log self-describing, as the architecture asks.

## Money and the ledger

8. **Cash unit = 1/10,000 of a tick·lot ($0.000001 with a $0.01 tick and 1-share lots).** A fee in whole bps of notional is then exactly `px × qty × bps`, with no rounding. `priority_fee` uses the same unit.
9. **The taker pays the taker fee on each fill. The sender pays its priority fee when the message is included, filled or not** (section 9). Agents only bid when the rule is PGA.
10. **Accounts start at 10^18 cash units and 10^9 lots. PnL is marked to the true Nasdaq price at the end of the run**, even if it ends while the price is hidden. Section 9 says "marked to the Nasdaq price"; the markout horizons in section 10 are phase 3.
11. **The zero-sum check holds by construction.** It catches ledger bugs (for example, a fee debited but never credited, which a unit test shows) but cannot catch a wrong fill from the engine. It is a bookkeeping gate, not a correctness proof.

## Randomness and determinism

12. **Each agent's RNG is `ChaCha8Rng::seed_from_u64(master)` with `set_stream((id << 8) | purpose)`.** Latency and decisions use separate purposes, and the feed is id 0 with its own diffusion and jump streams. This follows section 4 and keeps outside inputs on their own streams.
13. **Floats appear only in the sim's samplers, through `libm` (pure Rust). `rand_distr` is not used.** `std`'s `ln`/`exp` (which `rand_distr` calls) go to the platform's math library, and results can differ in the last bit between machines. Every draw becomes integer ns or lots immediately, and the engine, ledger and metrics have no floats.
14. **"20 ± 5 ms" means uniform in [15, 25] ms, drawn in whole ns.** It is the simplest bounded jitter.
15. **One send-latency draw per reaction: all messages from one reaction arrive together, in order.** Otherwise an LP's cancels and new quotes could interleave with other traffic.
16. **Each agent's see and send channels are FIFO: a delivery is never earlier than the previous one.** One connection per agent, and it stops an agent seeing an older price after a newer one.

## Price feed and calendar

17. **Diffusion is ±1-tick steps arriving as a Poisson process at 1/s** ("about 1 tick per second"). Jumps are Poisson at 1/300 s, sized uniformly from 5 to 20 ticks, with a random sign.
18. **The hidden weekend has diffusion only (no jumps) at 0.1 steps/s, so the gap's standard deviation is about 150 ticks (1.5%) over 65.5 h.** Section 16 leaves weekend volatility open, and 1.5% is a typical single-stock weekend gap.
19. **Piecewise rates (weekday/weekend, "jumps start after") are sampled exactly**: a draw that crosses a boundary restarts there, which is valid because the process is memoryless.
20. **A visible `Tick` at t = 0 carries the start price**, so agents have something to quote around.
21. **Scenario timing.** Calm weekday: 1 h, with "no jumps for the first minutes" taken as 10 min. News jump: 120 s, diffusion on, one +20-tick jump at 60 s. Monday open: t = 0 is Friday 15:00 ET, then 1 h visible, 65.5 h hidden and 30 min of Monday.

## Sequencer

22. **With B = 0, each message is sequenced on arrival and the block number counts messages.** "Every message is its own block."
23. **`BlockClose` is scheduled when the first message enters a block**, not every B. The semantics are the same, and it avoids millions of empty events over a 67 h run.
24. **A tick's `block` field is the block open at its time (t / B), or the current counter when B = 0.** Ticks never wait for a block (section 6).
25. **Messages still in an open block when the run ends are never sequenced.** They are counted as `unsequenced` in the summary.

## Agents

26. **The LP learns its order ids from the `Accepted` events it sees.** On a requote it cancels every order it knows about and marks unacknowledged orders obsolete, then cancels those when their acks arrive. Ids are `seq`, so it cannot cancel an order before it has seen the ack.
27. **The LP re-posts a filled level of its current quote at the same price** (and tops a capped side back up, entry 50). The spec doesn't say. Without refills, the weekend book drains within minutes, because no ticks arrive to trigger a requote.
28. **The inventory cap is checked against inventory from fills the LP has seen.** A side is skipped if filling all of it would push inventory past ±cap.
29. **The LP learns of the close from the calendar, without latency, and widens ×3 by scaling every offset.** On the first visible tick after the reopen it requotes at normal width, even if the price moved less than 1 tick.
30. **Snipers act only when they see a price**, as section 8 states, using their own late view of the book built from `BookChange` events. They send one IOC per stale side, sized to all the stale quantity. The expected prize is Σ (seen − px) × qty, and the PGA bid is α of it, with α in bps (5000 = 0.5).
31. **Regular traders read the live book when they decide.** The spec gives them no see-latency. They skip an arrival if the opposite side is empty, but still make every draw so their streams stay the same under every rule. Size is lognormal with median 2 and σ = 1 (σ unspecified), rounded and capped at 50. There is one regular-trader agent at 0.5/s.

## Metrics

32. **Races are counted per LP order.** A race starts at a logged `Tick` that leaves the order stale by ≥ θ. It ends as an LP win on the LP's own cancel (or a self-trade cancel), a sniper win on a sniper fill, or "other" on a regular trader's fill. A partial sniper fill ends the race, and the remainder can start a new one.
33. **LP race win rate = LP wins ÷ resolved races (LP + sniper + other); races still open at the end are excluded.** "All races" can't include races with no outcome.
34. **The summary adds each class's gain on its fills against the true price at the moment of the fill** (a horizon-0 markout, before fees). It isolates the stale-quote prize from inventory noise. Proper markouts at 1/10/60 s are phase 3.

## Gates

35. **Budish setup: races in isolation.** One LP and N snipers, jumps only (0.2/s, no diffusion), no regular traders, no inventory cap, LP latency equal to the snipers', 8 seeds × 1 h each. With diffusion on, two quick steps give the LP a head start (its first cancel is already in flight), which is a real effect but not the one the check is about.
36. **Budish tolerance: 4 binomial standard errors on episodes** (jumps), not races. All races in one episode go to whoever is sequenced first, so episodes are the independent trials.
37. **"Every message in one block" means B = 1 s.** That puts each race's messages, a few ms apart, in one block, except when they straddle a block boundary; the threshold is ≥ 95%. A B as long as the run would never execute anything.
38. **Golden hashes are an insta snapshot of the log and fills sha256** per scenario × rule × B ∈ {0, 250 ms} × seeds {1, 2}. There is a CI workflow file, but no remote exists, so it has not run in CI.
39. **"Shrinking every latency in proportion must not change the sniper take" holds only when races don't overlap price moves; spec rev 36 now scopes it to isolated races.** The gate test is `budish_isolated_races_latency_scaling_keeps_sniper_take`. In the isolated setup, ×1/2 and ×1/10 change the sniper take by +0.30% and −0.07%, which passes. In calm weekday, ×1/10 lowers it about 10%, because diffusion runs on an unscaled clock. The check therefore runs on the isolated setup and measures take at fill time; the end-of-run mark varied ±7% from inventory alone.
40. **Spec issue (resolved by spec rev 36): with B > 0, a quote whose cancel was already in flight counted as a race the LP "won".** A cancel only takes effect at block close, so the next tick made the quote stale and started a race the cancel then "won": in calm weekday under FCFS the LP race win rate went 0.21 → 0.55 → 0.84 → 0.93 for B = 0, 50, 250, 1000 ms (20 seeds). Section 10 now says such a quote doesn't start a race. `RaceTracker` skips a quote at a tick if a cancel for it reached the sequencer strictly before the tick's time (the sim reports arrivals when the sequencer accepts them; a replay can read them from the `Cancel` records' `t_ns`, which is equivalent). After the fix the rate is 0.212, 0.201, 0.213, 0.216: flat in B (0.213, 0.201, 0.233, 0.203 after entry 50's LP change). Check: `cargo run --release -p sim --example fcfs_block_check -- 20`.
41. **With B = 0, the three rules order messages identically** (each block holds one message). PGA then differs only in fees paid, and cancel priority equals FCFS; the golden fills hashes show this.
42. **Spec issue: under FCFS, B still changes the sniper take at 1 s, and the race count misses why.** After entry 40, the LP win rate is flat in B, but in calm weekday (20 seeds, after entry 50) the snipers' take at fill time is $20.56, $20.66, $21.51 and $34.52 per hour for B = 0, 50, 250, 1000 ms (+0%, +5%, +68%), on 419, 441, 542 and 1,781 filled lots. Of the 1,781 lots at 1 s, 1,328 hit an LP quote that was already stale when it entered the book (vs 2.8 at B = 0), and 1,442 hit a quote that entered the book in the same block as the sniper's order. Sniper race wins fall from 55 to 38 per hour at 1 s because those quotes never start a race. Mechanism: the LP posts quotes around the price it saw, they wait up to B for their block, and the price moves meanwhile (about 1 tick/s); at block close they rest already stale, and a sniper IOC later in the same block (limit = seen − θ, which sweeps every ask at or below it, including quotes the sniper never saw) takes them. The LP cannot cancel them in that block, because an order id is its `seq` (entry 1) and the LP learns it only from the ack after the block seals (entry 26), so a fresh quote is exposed for at least one block. No price move makes a resting quote stale, so these fills are not races under section 10; they still count in sniper take. This is a genuine effect of blocks in this model, not a counting bug: B lengthens the LP's effective reaction time for new quotes. It would shrink if orders carried client-chosen ids cancellable in the same block. The grid keeps the spec's definitions; the report and the chart show the FCFS line moving at B = 1 s. Check: `cargo run --release -p sim --example fcfs_block_diag -- 20`.

## Phase 3: metrics

43. **Metrics are computed from the log by a replay (`metrics::measure`), plus three inputs the log does not hold:** the true price path (the hidden weekend is never logged), each message's decision time (the log has arrival times), and run parameters (B, θ, taker fee, calendar). A block message is processed at its block's close, (block + 1) × B. The races counted by the replay equal the simulation's online count, and horizon-0 transfers equal `take_at_fill` (gate test `metrics_agree_with_the_simulation`).
44. **Markout horizons h ∈ {0, 1 s, 10 s, 60 s}; headline numbers use h = 1 s**, the shortest horizon in section 10 (h = 0 is the instant prize, kept for checks). A markout past the end of the run uses the last price.
45. **Sniper take = the snipers' PnL at h, net of taker and priority fees** (section 10's formula). **LP loss to snipers** (the main chart) = the snipers' gross gain on fills against LPs at h, before fees: what the LP loses, whoever keeps it in the end, so under PGA it doesn't shrink when the prize goes to the chain (H2). "bps of volume" divides by Σ p·q over all fills. "$ per day" scales by 24 h ÷ run length, since the on-chain book trades around the clock.
46. **LP adverse selection uses v, not the book mid, as the reference.** With s = +1 when the LP sold: effective = Σ q·s·(p − v at fill), realized(h) = Σ q·s·(p − v at fill + h), adverse selection = effective − realized = Σ q·s·(v at fill + h − v at fill), in bps of LP notional. Section 10 values every fill against v.
47. **Regular-trader cost = Σ q·d·(p − v at decision) over their fills, in bps of their notional, price only** (fees are reported on their own). **Fill delay = processing time − decision time per taker order with at least one fill**, nearest-rank median and p99; the headline is regular traders' orders, snipers' are kept too.
48. **Quoted liquidity is time-weighted over the whole run.** Half-spread in bps = Σ(ask − bid)·dt ÷ Σ(ask + bid)·dt over the time both sides are quoted (a ratio of integrals keeps the core integer), with the two-sided share of time reported next to it. Depth = lots resting within ⌊10·v / 10⁴⌋ ticks of the true v on both sides, averaged over the run.
49. **Monday-open take: the denominator uses the side the gap makes stale** (asks if the gap is up, bids if down): |gap| × lots resting there at Friday close. The numerator is the snipers' PnL (h = 1 s, net of fees) on fills processed in [reopen, reopen + W). W is a measurement option (`RunOpts`, default 5 min), not scenario config, so changing it doesn't change the log. The share can exceed 1: refills and the second level also get sniped inside W, and the book at the reopen need not equal the book at the close.
50. **Spec issue (agent behaviour change): the LP brings a side back once the inventory cap allows it.** Section 8 says the LP "stops quoting the side that would push inventory past the cap". Phase 2 re-checked the cap only on a requote (a price move) or a refill, so a side the cap emptied or thinned stayed that way until the next price move. Over the hidden weekend there is none, and 65.5 h of uninformed flow pins inventory near the cap: in 6 of 6 Monday-open seeds the stale side held 0 or 1 lot at the reopen, so the Monday-open take was about 0 and H4 could not be tested. Now, after its refills, the LP tops every level of its current quote back to full size on any side whose full ladder fits the cap. When the cap does not bind, the refills already restored every level and the top-up posts nothing. After the change the stale side holds 15 lots at the reopen in those seeds and the Monday-open take is 0.96 to 1.12 of the gap. Golden hashes: the log and fills hashes of every calm_weekday and monday_open row changed (24 of 36; the cap binds in calm weekday too, which was two-sided only 89 to 96% of the time); news_jump is unchanged.

## Phase 3: grid and chart

51. **The grid runner is its own crate (`crates/grid`, binary `grid`).** Section 11 puts parquet reports under `metrics`, but arrow and parquet would then sit next to the integer core and slow every test build. `grid` is the report layer: floats, bootstrap and the wall clock (for the runtime line) live there and never inside a run.
52. **Speed gap = every sniper latency (see and send, base and jitter) set to the LP's × gap**; the LP keeps the spec defaults (see 20 ± 5 ms, send 3 ± 1 ms). The spec's default snipers (8 ms vs the LP's 23 ms, a gap of about 0.35) are not a grid level.
53. **Regimes are `calm_weekday.toml` (1 h) and `monday_open.toml` (Friday 15:00 to Monday 10:00).** The main chart's value is LP loss to snipers at h = 1 s in bps of volume over the same span: the whole hour for the weekday, and the first W = 5 min after the reopen for the Monday open. Over the whole Monday run it would divide by 65.5 h of weekend volume and hide the reopen; that number is in `grid_runs.parquet` as `lp_loss_run_*`.
54. **Intervals are percentile bootstraps of the mean over seeds** (2,000 resamples, a fixed resampling stream per cell, so the summary is reproducible). Rules are compared by paired differences on the same seeds; a pair is "separated" when the 95% interval of its paired difference excludes 0. B = 0 groups are left out of the ranking: one message per block orders the rules identically (entry 41), so their LP loss is equal by construction.
55. **Headline cells: B = 250 ms, speed gap 0.5, 3 snipers.** B = 0 makes the rules identical, 0.5 is the grid level nearest the spec's default latencies, and 3 is the spec's sniper count. The main chart uses the same gap and sniper count; `main_chart.py --gap --snipers` draws the others.
56. **Seed count: 200 per cell, from a 20-seed pilot.** The pilot (4,320 runs, 80 s on 8 threads) gave per-cell SDs of LP loss of about 0.03 to 0.09 bps on weekday cells (means 0.02 to 0.78) and 0.9 to 2.4 bps on Monday-open cells (means 0 to 3.6; the gap size varies by seed, which paired seeds mostly cancel). Requiring the 95% interval of each paired difference to be no wider than half the difference, 149 of 162 B > 0 comparisons needed ≤ 20 seeds, the hardest finite ones needed about 40 to 250, and five needed more than 200 (all FCFS vs PGA on the Monday open with equal speed, mean differences of 0.1 to 0.3 bps on an SD of 1 to 2). 200, the spec's starting point and the cap, covers everything but those near-ties and takes 14 min of wall time (43,200 runs, about 150 ms per run per thread, Monday runs dominating).
57. **Phase 3 gate: passed for the main chart, 160 of 162 pairs grid-wide.** With 200 seeds, every rule pair on LP loss is separated in 52 of the 54 B > 0 groups, including all six main-chart groups. The two exceptions are FCFS vs PGA on the Monday open at equal speed (B = 50 ms with 10 snipers, B = 250 ms with 3), with paired differences of −0.04 [−0.22, 0.10] and −0.08 [−0.35, 0.17] bps: statistical ties, not a lack of seeds (they would need about 9,000 to 12,000 seeds).
58. **Finding, not a bug: under PGA the snipers' fees exceed the prize, so sniper take is negative.** Each sniper bids α = 0.5 of the prize it sees on every IOC and pays on inclusion, filled or not. With 3 snipers racing for one quote, the fees add up to about 1.5× the prize, plus IOCs that find nothing: on the weekday at B = 250 ms the chain takes 0.86 bps of volume while the LP loses 0.50 to snipers, and the snipers net −0.68 bps. This is the fixed α of section 8, not an optimised strategy.
59. **Caveat on the Monday-open line: bps of the window's volume ranks PGA below FCFS, dollars do not.** At B = 250 ms (gap 0.5, 3 snipers) LP loss is 3.64 bps under FCFS and 2.96 under PGA, but $18.37 [16.69, 20.05] vs $20.19 [18.51, 21.89] in dollars, because PGA raises the window's volume. `summary.py` prints the dollar values next to the headline table; the slide should say which one it shows.

## Phase 4: live mode, server and benchmark

60. **Live control changes are a fourth record kind, `Config { param, value }`, in the same input log.** Section 12 asks for "a logged config event" but section 4's record has no kind for one. The engine treats it as opaque: it takes a `seq` (so it sits at an exact place in the order) and produces no events; `sim::Control` gives `param` its meaning (1 rule, 2 B in ms, 3 load multiplier, 4 playback speed in thousandths, 5 stop). The wire kind is appended last, so postcard encodes every other kind exactly as before and every existing log, and golden hash, is byte-identical; `FORMAT_VERSION` stays 2 (a reader without the variant fails loudly on a log that has one). Config records are processed at their arrival time, like ticks, in `metrics::processed_ns`.
61. **A control applied at virtual time t takes effect after every event at or before t, and is logged with `t_ns = t`.** `sim::Live` advances the event loop to a time the harness picks (from the wall clock and the playback speed), then applies controls; `sim::replay` re-runs scenario + seed with each `Config` record applied at its `t_ns`, and checks it lands on the same `seq`. The effects: **rule**: the sequencer sorts blocks by the new rule from the next close (open blocks included), and LPs and snipers learn it at once (it is a public protocol parameter, like the calendar close), so PGA bidding starts with the switch; **B**: every open block closes now, sorted by the current rule, and numbering restarts after the last block used, so block numbers keep increasing and a stale close event finds nothing; **load**: the regular traders' rates are multiplied and each trader's next arrival is redrawn from now (exact for a Poisson process; the arrivals already queued are dropped by a generation counter); **speed**: changes nothing in the simulation, logged so a replay can also reproduce the demo's pacing; **stop**: the run ends there, and a replay stops at it. A run without controls is unchanged: `run` is now `start` + `advance_to(end)`, block numbering is t / B until B changes, and the load factor is exactly 1.0. Gate tests: `crates/sim/tests/live.rs` (live = batch byte for byte; a run with 13 changes of every kind replays to the same log bytes and fills hash, by re-simulation and by engine replay, on 3 seeds).
